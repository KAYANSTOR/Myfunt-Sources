# Myfnt 2.12.7 — Step21J Lazy Domain Hydration

## الهدف
تحويل التطبيق من نموذج يحمّل كامل الحجوزات والعملاء والسندات إلى RAM عند بدء التشغيل، إلى نموذج هجين يحافظ على واجهات النظام القديمة كـ Working Set صغير بينما تصبح IndexedDB المصدر الفعلي للقراءات الثقيلة.

## IndexedDB Schema 8
- `customers.company_customer_no` للفهرسة حسب الشركة ورقم العميل.
- `bookings.company_updated` للفهرسة حسب الشركة وآخر تحديث.
- `payments.company_amount` للفهرسة حسب الشركة والمبلغ.
- حقول denormalized/search summary جديدة في الحجوزات والعملاء والسندات الجديدة، بدون فرض ترحيل جماعي ثقيل على السجلات القديمة.

## Adaptive Hydration
يدخل التطبيق وضع Lazy Domain تلقائيًا إذا تحقق أحد الحدود التالية:
- أكثر من 6,000 حجز.
- أكثر من 8,000 عميل.
- أكثر من 8,000 سند/دفعة.

في الوضع الكسول:
- يتم Hydration للإعدادات والباقات والجداول الصغيرة بالكامل.
- يتم تحميل Working Set للحجوزات من 120 يومًا سابقًا حتى سنتين مستقبلًا.
- الحد الأعلى الافتراضي لمجموعة العمل: 5,000 حجز.
- لا يتم تحميل جميع العملاء والسندات القديمة إلى الذاكرة، بل فقط المرتبط منها بمجموعة العمل أو المطلوب عند الطلب.

## المالية
- سجل الحركات أصبح paged مباشرة من IndexedDB.
- البحث والحالة والترتيب تتم بدون نسخ كامل جدول الدفعات إلى RAM.
- إحصاءات المقبوض والمنصرف والصافي والمتبقي تحسب من قاعدة البيانات المحلية.
- فتح سند غير محمّل يستدعي `ensurePayment()` ويضيف السند وسياقه إلى Working Set فقط.
- سجل تدقيق السند `payment_audit` يقرأ من IndexedDB عند الطلب، ثم يدمج مع تعديلات الجلسة الحالية.

## العملاء
- قائمة العملاء أصبحت paged من IndexedDB.
- بطاقة العميل تقرأ ملخصًا فقط: عدد الحجوزات، النشطة، آخر تاريخ، والإجماليات حسب العملة.
- لا يتم تحميل تاريخ 25 عميلًا كاملًا لمجرد عرض الصفحة.
- فتح عميل واحد يستدعي `ensureCustomer()` ويجلب حجوزاته وسنداته عند الحاجة.
- مطابقة الاسم + الهاتف قبل إنشاء العميل أصبحت تقرأ IndexedDB حتى لو لم يكن العميل في RAM.

## البحث
- البحث الموحد في الحجوزات يقرأ IndexedDB مباشرة في الوضع الكسول.
- دعم سجلات Step21J الجديدة عبر `search_text`.
- السجلات القديمة من 2.12.6 وما قبلها تستخدم fallback إلى `booking_details` بدل فرض Backfill ضخم أثناء التحديث.
- فتح نتيجة بحث يجلب الحجز وسياقه إلى Working Set قبل المعاينة/التعديل.

## التصدير والنسخ الاحتياطي
- JSON / CSV / النسخة الاحتياطية / Daily Save / تصديرات الإدارة لا تعتمد على Working Set.
- عند طلب تصدير كامل يتم إنشاء Snapshot كامل من IndexedDB عند الطلب فقط ثم تحريره بعد انتهاء العملية.
- هذا يبقي التشغيل اليومي خفيفًا، مع الحفاظ على اكتمال ملفات التصدير.

## أرقام الكيانات
تم نقل توليد أرقام العرض في وضع البيانات الكبيرة إلى عدادات ذرية داخل IndexedDB:
- booking
- customer
- receipt
- movement

السبب: `MAX()` على Working Set ناقص قد يعيد استخدام رقم موجود قديمًا وغير محمّل. العداد المحلي الذري يمنع ذلك، ويعمل أيضًا عبر التبويبات.

## الحماية من التعارضات
- قبل فحص تعارض يوم الحجز، يتم تحميل نفس اليوم/الشهر من IndexedDB وإدخاله مؤقتًا إلى Working Set.
- يمنع ذلك قبول حجز مكرر فقط لأن الحجز القديم لم يكن محمّلًا في RAM.
- حماية تعدد التبويبات من Step21H ما زالت فعالة عبر BroadcastChannel + fallback signal.

## التوافق
- الشركات الصغيرة تظل على Full Hydration لتقليل أي مخاطرة أو تغيير سلوكي غير ضروري.
- الشركات الكبيرة تنتقل تلقائيًا إلى Lazy Domain.
- لا يوجد Migration جماعي إلزامي للسجلات القديمة؛ الحقول الجديدة تتحسن تدريجيًا مع الحفظ والتعديل.

## ملاحظات أداء
- التشغيل الطبيعي لا يحمل التاريخ المالي والعملاء كاملًا.
- التصدير الكامل بطبيعته يحتاج Snapshot كامل مؤقتًا؛ لذلك قد يستهلك ذاكرة أعلى أثناء عملية التصدير فقط، وليس طوال الجلسة.
- شاشة إدارة الحجوزات العامة ومحرك الإشعارات ما زالا يعتمدان على Working Set في التشغيل المرئي؛ انتقالهما إلى Query-Driven Runtime مناسب لخطوة لاحقة منفصلة حتى لا نوسع مخاطرة Step21J.
